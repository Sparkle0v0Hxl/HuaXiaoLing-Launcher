## 三、卸载问题的真相（用户 2026-11-26 报「点卸载还是旧的」）

**用户原话后的澄清**：「我说的卸载还是旧的，意思就是我在用的正式版本，点卸载是旧的」。

### 根因
正式版（v2.13.1 及之前）是用**旧 NSIS 安装器**打包的。NSIS 的 `oneClick:false + allowToChangeInstallationDirectory` 会写自己的卸载项：
```
UninstallString = "<安装目录>\Uninstall 花筱灵启动器.exe" /currentuser
```
所以用户点「卸载」跑的是 NSIS 卸载器 —— 这是旧界面，符合预期。

### 注册表实况（2026-11-26 22:04 实测）
`HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall` 里名字带「花筱」的**只有一条**：

| 字段 | 值 |
|---|---|
| 键名 | `e5868757-45fc-5dcb-b67a-077e038e1e8d` |
| DisplayName | 花筱灵启动器 2.8.0 |
| DisplayVersion | 2.8.0 |
| Publisher | HuaXiaoLing Studio |
| UninstallString | `"H:\新建文件夹\huaxiaoling-launcher\Uninstall 花筱灵启动器.exe" /currentuser` |
| QuietUninstallString | `... /currentuser /S` |
| DisplayIcon | `H:\新建文件夹\huaxiaoling-launcher\花筱灵启动器.exe,0` |
| EstimatedSize | 402680 |

**这条是 2.8.0 的僵尸项，指向的目录 `H:\新建文件夹\huaxiaoling-launcher` 已经不存在** → 点它必然失败。

三条期望键名全不存在：`huaxiaoling-launcher` / `com.huaxiaoling.launcher` / `com.huaxiaoling.installer`
→ 说明**新自绘安装器从来没在真机跑过完整安装流程**。

### 卸载代码链路（已完整，别以为是没写）

## 九、🔴 本轮修的关键 bug：pack.js 发布的是旧 NSIS 安装器

### 问题
`pack.js` 的 `electron-builder` 步骤（L400）用 package.json 的 build 配置跑 NSIS，产出 `HuaXiaoLing-{ver}-Setup.exe`。
然后 L421-431 调 `buildInstaller()` 产出 `HuaXiaoLing-{ver}-Setup-Custom.exe`。
**两个 Setup 同时在 dist 里**，而 L437 的查找是：
```js
const setup = files.find((f) => /^HuaXiaoLing-.*-Setup\.exe$/i.test(f));
```
这个正则**只匹配 `-Setup.exe`（NSIS 版）**，匹配不到 `-Setup-Custom.exe`。
→ 最终发布出去的是**旧 NSIS 安装器**，新自绘安装器白做。
→ 用户装了发布包，卸载自然还是旧 NSIS 装卸器 —— 这就是「点卸载还是旧的」的另一半原因。

### 修法（已改 2026-11-26 22:27）
```js
let setup = files.find((f) => /^HuaXiaoLing-.*-Setup-Custom\.exe$/i.test(f));
if (!setup) setup = files.find((f) => /^HuaXiaoLing-.*-Setup\.exe$/i.test(f));
```
改名时也要先删同名目标（Windows 上 renameSync 遇到已存在目标会 EPERM）：
```js
if (setup !== setupName) {
  const setupTarget = path.join(DIST, setupName);
  if (fs.existsSync(setupTarget)) fs.rmSync(setupTarget, { force: true });
  fs.renameSync(path.join(DIST, setup), setupTarget);
}
```
`node --check pack.js` 通过。

### 打包时 dist 里会有什么（预期）
```
dist\
  HuaXiaoLing-2.14.0-Setup.exe          ← 最终发布的（= Custom 改名而来）
  HuaXiaoLing-2.14.0-Setup-Custom.exe   ← 会被改名，正常不留
  HuaXiaoLing-2.14.0-Portable.zip
  delta-…-to-2.14.0.zip / .json
  win-unpacked\
  latest.json
```
`pack.js:374-378` 的「清理旧产物」会先 `fs.rmSync(DIST)` 清空整个 dist，所以不会有上一版残留混淆。

## 十四、🔴 payload 暴涨到 6.1GB 的根因：备份文件无限堆积（两个 bug 已修）

### 现象

第一次跑 `node H:\HXL-pack\installer-build.js --unpacked "H:\花筱灵启动器"`，
`填充 payload` 卡了 14 分钟还没完。检查发现 payload 已经 **159,158 个文件 / 6100.9 MB**（正常应是 4183 文件 / 94MB）。

### 根因 1：同步脚本每跑一次留一份完整备份，从不清理

`H:\花筱灵启动器-源码\.tmp\sync-runtime-asar.js` 里：
- L588-589：每次同步都 `fs.copyFileSync(target, `app.asar.bak-${stamp()}`)`（49.6MB × 69 份 = **3.5GB**）
- extraResources 循环里：`netease-api.bak-<stamp>`（43.5MB × 64 份 = **2.77GB**）、
  `updater.bak-*`（64 份）、`elevate.exe.bak-*`（64 份）、`azur-channel.bak-*`（41 份）

**这两个文件在运行副本里实际堆积：302 份备份，合计 6.28 GB。**
用户磁盘会随着每次同步单调减少 —— 这是真实的磁盘泄漏，不只是打包问题。

**修法**（`_fix-sync-backup2.js` / `_fix-sync-backup3.js`）
- 新增 `function pruneBackups(dir, baseName, keep = 3)`（插在 `stamp()` 之后，32 行）：
  列出 `<baseName>.bak-<14位数字>`，按名字排序（时间戳天然有序），
  删掉除最近 `keep` 份之外的，失败不报错（下次再清）。
- 三处调用点：①`app.asar` 备份后 ②extraResources 目录分支（rename 成 bak 后）
  ③extraResources 文件分支（copyFile 成 bak 后）。
- `node --check` 通过。

### 根因 2：installer-build.js 直接 cpSync 整个 resources

原代码 `fs.cpSync(srcResources, path.join(payload, 'resources'), { recursive: true })`
把 resources 里的一切都搬进安装包，包括：
- 上面那 6.28GB 备份
- `endfield-packs\` **670.8 MB**（终末地渠道包缓存，属于运行时数据）
- `lx-sources\` 0.5 MB（**用户自己导入的音源脚本，绝不能进安装包**）

**修法**（`_fix-installer-payload.js`）
改成白名单复制，只搬这 7 项：
`app.asar`、`app.asar.unpacked`、`netease-api`、`updater`、
`elevate.exe`、`azur-channel`、`app-update.yml`；
命中不足 3 项直接 fatal（防 resources 结构被改坏后静默出错）。

### 清理与重建结果

| 项 | 前 | 后 |
|---|---|---|
| 运行副本 resources 体积 | 6.3 GB | 764 MB（含 endfield-packs 670MB + 用户数据） |

### Setup.exe 已产出

```
H:\HXL-pack\dist\HuaXiaoLing-2.14.0-Setup-Custom.exe   164.7 MB   2026-11-26 23:36:28
```

payload 白名单命中 7/7 项，electron-builder 出包成功（exit 0）。

### 教训

1. **备份策略必须有上限**：任何「改之前先备份」的脚本都要配一个「只留 N 份」的清理，
   否则同步次数一多就变成磁盘黑洞。
2. **打安装包不能整个目录 cpSync**：运行副本里必然混着用户数据、缓存、备份，
   必须白名单。白名单还有个额外好处 —— 结构被改坏时会因为「命中数不足」立刻报错，
   而不是打出一个 6GB 的包才发现。
3. 这两个 bug 都是**先量后改**才发现的：不看 payload 体积和文件数，光看日志「填充 payload…」
   会以为是正常慢。

旧方案（2026-11-25 之前）是安装器把自己复制一份成 `安装目录\Uninstall.exe`。但 Electron 的规则是「执行文件同目录下的 `resources\app.asar` 就是我的程序」，而安装目录里的 `app.asar` 是**启动器本体** —— 双击那个 Uninstall.exe 跑的是启动器主界面，就是用户报的「卸载里掺进安装」。

复制一份还多占 250 MB。

硬链接：同一个文件的另一个目录项，字节完全一致、**不额外占空间**，Electron 按 `process.execPath` 找 resources，路径就在安装目录，能正常加载启动器的 asar。

限制：**硬链接没法带命令行参数**（双击就是裸启动，`argv` 里没有 `--uninstall`）。所以主程序改成按 exe 文件名也认卸载模式。

## 第十九节 · 老用户永久卡住的真 bug（迁移 v2 → v3）与 hosts 拦截构建（2026-11-27 06:56–07:53）

### 1. 根因一：判断逻辑「有同名文件就跳过」

`electron/migrations.js` 的 `uninstall-shortcut` 分支原文：

```js

  result.skipped += 1;
  if (!dryRun) { markers[entry.id] = { ok: true, note: 'already exists' }; changed = true; }

```

老用户的 `H:\花筱灵启动器\Uninstall 花筱灵启动器.exe` 是 **2.8.0 时代 NSIS 安装器留下的 363044 B 旧件**
（ProductName=花筱灵启动器 / FileVersion=2.8.0 / mtime 2026-11-02 16:07）。
只要文件在，就判「已存在」→ 写 `ok: true` 标记 → **从此永不重跑**。
结果：老用户更新到 2.14.0 后点卸载，看到的还是旧 NSIS 界面，甚至没反应。

### 2. 根因二：标记已被污染

`H:\花筱灵启动器\data\.migrations.json` 里已经有 `uninstall-shortcut-v2: { ok: true, note: "link" }`
（我早期手工测试写的）。条目级标记的判定是：

```js

```

**即使修好判断逻辑，这批人也不会重跑。** 光改代码不够，必须让标记失效。

### 3. 修法 A：先分辨「这个卸载入口是谁的」

判据 = **大小相同 + ino 相同**（非 NTFS 复制场景退化为只看大小）：

```js
let ours = false;
try {
  const a = fs.statSync(appExe);
  const b = fs.statSync(uninstExe);
  ours = a.size === b.size && Number(a.ino) === Number(b.ino) && Number(a.ino) !== 0;
  if (!ours && a.size === b.size) ours = true; // 非 NTFS 退回复制时 ino 不同，大小相等也认
} catch { ours = false; }
if (ours) { skipped++; /* 写 ok */ continue; }
```

363044 B 旧 NSIS vs 250004480 B 主程序 → 大小不同 → 判为旧版 → 先 `fs.rmSync` 删掉再重建。
删不掉（杀软占用）记 `failed`，下次启动再试，**不写 ok 标记**。

### 4. 修法 B：换 id 让污染标记失效

迁移 id `uninstall-shortcut-v2` → **`uninstall-shortcut-v3`**。

条目级标记是按 id 存的，**改 id 等于新增条目**，老用户的 v2 标记不再匹配，v3 会重新执行一次。
（代码里加了 6 行注释写明 v2 到底错在哪，免得以后有人以为换 id 是多余的。）

- `26 none 状态不应带 officialOnly`

### 11. 教训

1. **「文件存在」不等于「文件是对的」。** 迁移判断必须先验身份（大小 + ino），不能只看路径存不存在。
2. **条目级标记是把双刃剑：** 它能保证幂等，但逻辑写错并跑过一次之后，标记会把错误永久固化。

3. **整包更新只覆盖程序文件，覆盖不了「安装器/卸载入口」这类外围文件。** 这类东西只能靠迁移补。
4. **构建工具默认联网。** 代理、hosts、缓存任意一环出问题都会让打包莫名其妙地失败；
   用 `electronDist` 把它钉死在本地是最稳的。

### 为什么只有走 SFX 才复现

这就是为什么之前本地反复验证安装器都「没问题」——只在解包目录里测，永远碰不到这条路。

### 修法

`H:\花筱灵启动器-源码\installer\main.js:282-294`（871 行，`node --check` 通过）：

```js
  /*
   * ★SFX（portable 外壳）用 SW_SHOWMINIMIZED 拉起子进程时，Electron 建出来的窗口会继承
   * 「最小化」状态：实测窗口位置 (-32000,-32000)、尺寸 160x28、IsIconic=true。
   * 用户在任务栏能看到图标，但点开是一片空白 / 看起来像「打不开」。
   * 所以 show 之后必须显式 restore + focus + moveTop，把窗口真正摆到前台。
   * （直接双击解包后的 exe 不受影响，所以本地只测解包版永远正常、只有走 SFX 才复现。）
   */
  win.once('ready-to-show', () => {
    win.show();
    if (win.isMinimized()) win.restore();
    win.focus();
    win.moveTop();
    setTimeout(() => {
      if (win && !win.isDestroyed()) {
        if (win.isMinimized()) win.restore();
        win.show();
        win.focus();
      }
    }, 120);
  });
```

第二层 120ms 延迟 restore 是保险：`ready-to-show` 里调 restore 有时还没生效（窗口还没真正 map）。

### 教训

1. **「打不开」先查窗口状态，别先怀疑文件损坏**。`EnumWindows` + `GetWindowRect` + `IsIconic` 三行就能分辨「没启动」和「启动了但最小化」。
2. **portable / SFX 外壳会改变子进程的窗口启动方式**。凡是在解包目录里测通的，都必须再用 SFX 双击验一遍——这两条路径不等价。
3. **最小化坐标是强信号**：`(-32000,-32000)` 一出现就说明是 `SW_SHOWMINIMIZED` 建的窗口，不必猜。
4. `ready-to-show` 里只 `show()` 不足以对抗继承来的窗口状态，必须 `restore()` + 延迟二次确认。

### 四、修法（三处，全在 `installer/main.js`）

1. **BrowserWindow 加 `alwaysOnTop: true` + `skipTaskbar: false`**

3. **点「开始安装」时解除置顶**（`ipcMain.handle('setup:install')` 开头）
   ```js
   try { if (win && !win.isDestroyed()) win.setAlwaysOnTop(false); } catch (e) { void e; }
   ```
   用户已经点到「开始安装」，说明界面看到了，解除置顶让它不再霸屏；
   **这同时保证了「安装过程我可以最小化掉它」不被置顶抵消**。

### 五、启动画面（解决「那么久才显示出来」）

portable = NSIS SFX，每次启动 `RMDir /r $INSTDIR` + `File /r` 解包 380MB（LZMA），
实测 **50~140 秒**期间屏幕上什么都没有 —— 这是「那么久才显示」的根因。

NSIS portable 模板支持 `SPLASH_IMAGE` 宏（`portable.nsi` 里 `.onGUIInit` 调
`BgImage::SetBg $PLUGINSDIR\splash.bmp`），electron-builder 对应配置项是 `portable.splashImage`。

生成 `installer/build/splash.bmp`：从 `installer/assets/bg.jpg`(2048x1152) 缩放到
**736x488 24bpp 无压缩 BMP = 1,077,558 B**（`54 + 736*488*3` 校验通过）。
**NSIS BgImage 只吃 24bpp**，`Graphics.FromImage` 直接画 32bpp 会抛 `Value cannot be null`（GetHdc 失败），
必须 `new Bitmap(w,h,PixelFormat.Format24bppRgb)` 再 `DrawImage`。

配置：
```json
"portable": {
  "artifactName": "${productName} Setup ${version}.${ext}",
  "splashImage": "build/splash.bmp",
  "unpackDirName": "huaxiaoling-setup"
}
```

**路径坑（折腾了两轮）**：`splashImage` 是**相对 projectDir（`installer/`）** 解析的，不是相对 `buildResources`。
写成 `"splash.bmp"` 会被解析成 `installer\splash.bmp`（不存在）→ makensis 报
`File: "...\installer\splash.bmp" -> no files found` + `Error in script "<stdin>" on line 98`。
正确写法 **`"build/splash.bmp"`**。

另外我当时误判过一次「没打进去」——用 ASCII 搜 exe 里 `splash.bmp` 与 1MB 级 `BM` 魔数都没找到。
**其实 BMP 被压在 LZMA 压缩体（`app-64.7z`）里，搜不到明文才是正常的。**
用 `_win5.ps1` 枚举窗口，看到 `CLS=[NSISBGImage] POS=912,296 SIZE=736x488 VIS=True` 才是真凭据。

### 六、实测四项（全部通过）

| 项 | 验证方式 | 结果 |
|---|---|---|
| 启动画面立刻出现 | `EnumWindows` 找到 `CLS=NSISBGImage` `736x488` `VIS=True` `POS=912,296` | ✓ |
| 窗口浮最前 | 主窗口 `EXSTYLE` bit 0x8（TOPMOST）= `TOP=True` | ✓ |
| 能最小化 | `ShowWindow(h, SW_MINIMIZE)` → `POS=(-32000,-32000) SIZE=160x28 ICONIC=True`；`SW_RESTORE` → 回 `(912,300) 736x488` | ✓ |
| 任务栏可见 | `EXSTYLE=0x00000000`（非 TOOLWINDOW）+ `OWNER=0` → 应该出现 | ✓ |

### 七、教训

1. **窗口「打不开」先做 Z-order 扫描**，不要只看自己的窗口状态。`Visible=True` / `IsIconic=False` / `DWM_CLOAKED=0` 全都正常却看不见，只能是别人盖住了。
2. **`PrintWindow` + 像素统计 vs 屏幕截图 `CopyFromScreen` 必须交叉验证**：前者证明「窗口自己画对了」，后者证明「屏幕上显示的就是它」。两者不一致 = 被遮挡。
3. **只测解包版等于没测**：portable/SFX 类安装器的窗口时序与普通 exe 完全不同，必须走完整双击路径。
4. **别用明文搜压缩包内容**：LZMA / 7z 压进去的东西 ASCII 搜不到，误判成「没打进去」会绕大圈。
5. **置顶必须配「可解除」**：用户要点最小化的东西不能一直压在别人上面，点开始安装就解置顶。

生成 `splash.bmp` 的 PowerShell 脚本长这样：

```powershell
$bmp = New-Object System.Drawing.Bitmap($w, $h, [PixelFormat]::Format24bppRgb)
$g = [System.Drawing.Graphics]::FromImage($bmp)      # ← 这里返回 $null
$g.InterpolationMode = ...                            # ← 静默跳过
$g.DrawImage($img, 0, 0, $w, $h)                      # ← 根本没画
$bmp.Save($dst, [ImageFormat]::Bmp)                   # ← 照样成功保存
```

**关键：`FromImage` 返回 `$null` 时，后续所有方法是 null 上的调用，PowerShell 报错但脚本继续往下走，
`$bmp.Save()` 仍然成功 —— 结果是一个 1,077,558 B、尺寸 736x488、24bpp 完全合法的 BMP，但像素全黑。**

我之前的校验只看了「文件大小 = 54 + 736*488*3」和「位深 = 24」，
这两个条件全黑图也满足，所以没能发现。

### 三、修法：改用 Electron 的 nativeImage

绕开有问题的 GDI+，用 Electron 自带的图像解码/缩放：

```js
const { app, nativeImage } = require('electron');
const img0 = nativeImage.createFromPath(SRC);                 // 2048x1152
const resized = img0.resize({ width: 736, height: 488, quality: 'best' });
const bgra = resized.toBitmap();                              // BGRA，top-down
// 手写 24bpp 无压缩 BMP 头 + BGR 像素（BMP 默认 bottom-up，要翻转行序）
```

运行方式：用安装器自带的那份 Electron 直接跑（`ELECTRON_RUN_AS_NODE` 先清掉）：
```
& 'H:\花筱灵启动器-源码\installer\node_modules\electron\dist\electron.exe' _mksplash-electron.js
```

### 四、新的校验方法（必须查像素，不能只看文件头）

回读 BMP，按 4 像素步长采样统计：
- 非黑像素占比（`r > 12 || g > 12 || b > 12`）
- 平均 R/G/B

正确输出：

| 新（nativeImage） | **100%** | (229,197,221) | 正常浅粉 |

### 六、教训

1. **「文件格式合法」不等于「图像内容正确」**：全黑 BMP 的尺寸/位深/文件大小全都对。必须查像素。
2. **PowerShell + GDI+ 在这台机器上不可靠**：`Graphics.FromImage` 会静默返回 `$null`。
   涉及图像处理优先用 Electron `nativeImage` / Node 库，别信 GDI+。
3. **静默失败最贵**：`$g.DrawImage(...)` 报错但脚本继续，`Save()` 成功，最后产物"看起来没问题"。
   任何图像生成脚本都必须带**内容回读校验**（非黑占比、平均色），不能只 `Test-Path` + 看 size。
4. **用户说的「黑幕」是一个精确的技术描述**，不是比喻。看到这种词要立刻想到「有个全黑窗口/图盖着」，而不是「加载慢」。
