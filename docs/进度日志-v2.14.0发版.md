## 三、卸载问题的真相（用户 2026-11-26 报「点卸载还是旧的」）

**用户原话后的澄清**：「我说的卸载还是旧的，意思就是我在用的正式版本，点卸载是旧的」。

### 根因
正式版（v2.13.1 及之前）是用**旧 NSIS 安装器**打包的。NSIS 的 `oneClick:false + allowToChangeInstallationDirectory` 会写自己的卸载项：
```
UninstallString = "<安装目录>\Uninstall 花筱灵启动器.exe" /currentuser
```
所以用户点「卸载」跑的是 NSIS 卸载器 —— 这是旧界面，符合预期。

### 注册表实况（2026-11-26 22:04 实测）
`HKCU:\Software\Microsoft\Windows\CurrentVersion\Uninstall` 里名字带「花筱」的**只有一条**：

| 字段 | 值 |
|---|---|
| 键名 | `e5868757-45fc-5dcb-b67a-077e038e1e8d` |
| DisplayName | 花筱灵启动器 2.8.0 |
| DisplayVersion | 2.8.0 |
| Publisher | HuaXiaoLing Studio |
| UninstallString | `"H:\新建文件夹\huaxiaoling-launcher\Uninstall 花筱灵启动器.exe" /currentuser` |
| QuietUninstallString | `... /currentuser /S` |
| DisplayIcon | `H:\新建文件夹\huaxiaoling-launcher\花筱灵启动器.exe,0` |
| EstimatedSize | 402680 |

**这条是 2.8.0 的僵尸项，指向的目录 `H:\新建文件夹\huaxiaoling-launcher` 已经不存在** → 点它必然失败。

三条期望键名全不存在：`huaxiaoling-launcher` / `com.huaxiaoling.launcher` / `com.huaxiaoling.installer`
→ 说明**新自绘安装器从来没在真机跑过完整安装流程**。

### 卸载代码链路（已完整，别以为是没写）

## 九、🔴 本轮修的关键 bug：pack.js 发布的是旧 NSIS 安装器

### 问题
`pack.js` 的 `electron-builder` 步骤（L400）用 package.json 的 build 配置跑 NSIS，产出 `HuaXiaoLing-{ver}-Setup.exe`。
然后 L421-431 调 `buildInstaller()` 产出 `HuaXiaoLing-{ver}-Setup-Custom.exe`。
**两个 Setup 同时在 dist 里**，而 L437 的查找是：
```js
const setup = files.find((f) => /^HuaXiaoLing-.*-Setup\.exe$/i.test(f));
```
这个正则**只匹配 `-Setup.exe`（NSIS 版）**，匹配不到 `-Setup-Custom.exe`。
→ 最终发布出去的是**旧 NSIS 安装器**，新自绘安装器白做。
→ 用户装了发布包，卸载自然还是旧 NSIS 装卸器 —— 这就是「点卸载还是旧的」的另一半原因。

### 修法（已改 2026-11-26 22:27）
```js
let setup = files.find((f) => /^HuaXiaoLing-.*-Setup-Custom\.exe$/i.test(f));
if (!setup) setup = files.find((f) => /^HuaXiaoLing-.*-Setup\.exe$/i.test(f));
```
改名时也要先删同名目标（Windows 上 renameSync 遇到已存在目标会 EPERM）：
```js
if (setup !== setupName) {
  const setupTarget = path.join(DIST, setupName);
  if (fs.existsSync(setupTarget)) fs.rmSync(setupTarget, { force: true });
  fs.renameSync(path.join(DIST, setup), setupTarget);
}
```
`node --check pack.js` 通过。

### 打包时 dist 里会有什么（预期）
```
dist\
  HuaXiaoLing-2.14.0-Setup.exe          ← 最终发布的（= Custom 改名而来）
  HuaXiaoLing-2.14.0-Setup-Custom.exe   ← 会被改名，正常不留
  HuaXiaoLing-2.14.0-Portable.zip
  delta-…-to-2.14.0.zip / .json
  win-unpacked\
  latest.json
```
`pack.js:374-378` 的「清理旧产物」会先 `fs.rmSync(DIST)` 清空整个 dist，所以不会有上一版残留混淆。

## 十四、🔴 payload 暴涨到 6.1GB 的根因：备份文件无限堆积（两个 bug 已修）

### 现象

第一次跑 `node H:\HXL-pack\installer-build.js --unpacked "H:\花筱灵启动器"`，
`填充 payload` 卡了 14 分钟还没完。检查发现 payload 已经 **159,158 个文件 / 6100.9 MB**（正常应是 4183 文件 / 94MB）。

### 根因 1：同步脚本每跑一次留一份完整备份，从不清理

`H:\花筱灵启动器-源码\.tmp\sync-runtime-asar.js` 里：
- L588-589：每次同步都 `fs.copyFileSync(target, `app.asar.bak-${stamp()}`)`（49.6MB × 69 份 = **3.5GB**）
- extraResources 循环里：`netease-api.bak-<stamp>`（43.5MB × 64 份 = **2.77GB**）、
  `updater.bak-*`（64 份）、`elevate.exe.bak-*`（64 份）、`azur-channel.bak-*`（41 份）

**这两个文件在运行副本里实际堆积：302 份备份，合计 6.28 GB。**
用户磁盘会随着每次同步单调减少 —— 这是真实的磁盘泄漏，不只是打包问题。

**修法**（`_fix-sync-backup2.js` / `_fix-sync-backup3.js`）
- 新增 `function pruneBackups(dir, baseName, keep = 3)`（插在 `stamp()` 之后，32 行）：
  列出 `<baseName>.bak-<14位数字>`，按名字排序（时间戳天然有序），
  删掉除最近 `keep` 份之外的，失败不报错（下次再清）。
- 三处调用点：①`app.asar` 备份后 ②extraResources 目录分支（rename 成 bak 后）
  ③extraResources 文件分支（copyFile 成 bak 后）。
- `node --check` 通过。

### 根因 2：installer-build.js 直接 cpSync 整个 resources

原代码 `fs.cpSync(srcResources, path.join(payload, 'resources'), { recursive: true })`
把 resources 里的一切都搬进安装包，包括：
- 上面那 6.28GB 备份
- `endfield-packs\` **670.8 MB**（终末地渠道包缓存，属于运行时数据）
- `lx-sources\` 0.5 MB（**用户自己导入的音源脚本，绝不能进安装包**）

**修法**（`_fix-installer-payload.js`）
改成白名单复制，只搬这 7 项：
`app.asar`、`app.asar.unpacked`、`netease-api`、`updater`、
`elevate.exe`、`azur-channel`、`app-update.yml`；
命中不足 3 项直接 fatal（防 resources 结构被改坏后静默出错）。

### 清理与重建结果

| 项 | 前 | 后 |
|---|---|---|
| 运行副本 resources 体积 | 6.3 GB | 764 MB（含 endfield-packs 670MB + 用户数据） |

### Setup.exe 已产出

```
H:\HXL-pack\dist\HuaXiaoLing-2.14.0-Setup-Custom.exe   164.7 MB   2026-11-26 23:36:28
```

payload 白名单命中 7/7 项，electron-builder 出包成功（exit 0）。

### 教训

1. **备份策略必须有上限**：任何「改之前先备份」的脚本都要配一个「只留 N 份」的清理，
   否则同步次数一多就变成磁盘黑洞。
2. **打安装包不能整个目录 cpSync**：运行副本里必然混着用户数据、缓存、备份，
   必须白名单。白名单还有个额外好处 —— 结构被改坏时会因为「命中数不足」立刻报错，
   而不是打出一个 6GB 的包才发现。
3. 这两个 bug 都是**先量后改**才发现的：不看 payload 体积和文件数，光看日志「填充 payload…」
   会以为是正常慢。
